## 2. Gesture: the Corrected Model Live

### 2.1 Which model
The user was advised to use `_trial_corrected` (Oct 5: 84.7% held out,
direction test 10/10):

```
python x7_gesture_live.py --host1 529 --host2 545 --calibrate 0 --model models/_trial_corrected.json
```

**Result:** SWIPE_LR was reported for SWIPE_RL and vice versa. The user
asked whether to invert the outputs, or whether the relabelling caused it.

### 2.2 First diagnosis (21 logged captures, `gesture_live_corrected/`)
Board-2 angle slope (energy-weighted slope of the unwrapped coherent angle
over the window). In the Oct 5 direction test, SWIPE_LR was positive 5/5 and
SWIPE_RL mostly negative.

| | board-2 slope |
|---|---|
| live captures reported SWIPE_LR | +0.6, +2.1, +6.8 (one −0.3) |
| live captures reported SWIPE_RL | −0.3, −0.5, −2.3 |
| energy in the first 8 frames, live | 0.5–0.7 of peak (movement already under way) |
| energy in the first 8 frames, direction test | ~0.1 (hand still) |

So the model reported the direction of the motion it captured. The live
windows started mid-movement. The hypothesis was that live captures the
**move into the start position**, which runs opposite to the swipe.

**Advice:** do not invert the outputs. Inverting would break any swipe that
is captured cleanly.

Two software fixes were proposed:
* **A:** if the opposite swipe follows within ~1 s, report only the second
  one.
* **B:** arm the trigger only after the hand has been still for ~0.5 s.

The user chose A, and also reported that a 2-second hold before each swipe
did not help.

### 2.3 A was not built: the evidence did not support it
34 captures from that run:
* **No pairs.** Captures came every 2–9 s, with no opposite-direction pair
  within 1–2 s. One capture per swipe.
* 19/34 were NO_GESTURE, and most left/right predictions had low confidence
  (0.38–0.77).
* Almost every window started with movement under way.

Fix A would almost never fire. It was put on hold pending a labelled test.

### 2.4 Labelled live-style test (`live_style_test/`, 12 captures)
```
python x7_gesture_record.py --host1 529 --host2 545 --auto --gestures SWIPE_LR SWIPE_RL --per-gesture 6 --no-gesture 0 --block 1 --out live_style_test
```
These are natural swipes with the automatic trigger, as in live, each one
labelled by the prompt.

| model | correct | reversed |
|---|---|---|
| `_trial_corrected` (relabelled) | **0/12** | 11 |
| `gesture_v3` (September labels as recorded) | **9/12** | 2 |

One capture per swipe; no pairs. On board 2, the natural SWIPE_LR swipes
(−0.5 to −1.0) look like the direction test's SWIPE_RL.

### 2.5 Which training labels work for which capture style
Small models (2 seeds, 50 epochs), September labels restored in memory:

| training labels | `live_style_test/` (automatic trigger) | `direction_test/` (Enter) |
|---|---|---|
| **September as recorded** | **10/12** | 1/10 |
| September as recorded + Oct 5 sessions (as performed) | 8/12 | 6/10 |
| September relabelled + Oct 5 (`_trial_corrected`) | 0/12 | 10/10 |

**Conclusion:** the two capture styles have opposite left/right signatures.
* **Natural swipe, automatic trigger:** the window holds movement already
  under way, including the move into position.
* **Enter-armed deliberate stroke:** the window holds the stroke alone.

Both were labelled correctly by what the user did. On Oct 5 the Enter-style
direction test was taken as ground truth. That led to relabelling the
September data, which was right for how the user actually swipes and for how
live detection captures. Mixing both styles in training (middle row) does
neither well, because one label then covers opposite-looking windows.

Each board's axis points mostly up/down at this mounting (Oct 5). The
left/right cue is weak, which is why the capture style can flip it.

object on a seat.

## 8. Lessons

**Ground truth must be captured the way the system is used.** The Oct 5
direction test was real and correctly labelled, but it captured a different
movement pattern from live use. Relabelling a week of data to agree with it
broke live detection.

**A model that agrees with a test is not proof the test represents reality.**
`_trial_corrected` scored 10/10 on the direction test and 0/12 on natural
swipes. Two test sets in two styles exposed it.

**Check that a fix's assumption holds before building it.** Fix A assumed two
captures per swipe; the logs showed one.

**When the user says "it works", record what it was tested with.**
`gesture_v3` had been called "trained on reversed labels" for a week. The live
result and `live_style_test/` showed it was right.
