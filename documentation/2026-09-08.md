# Engineering Log — Dual-Sensor X7 Radar Gesture Recognition
**Date:** September 8, 2026

---

## 1. Objective

Fix live gesture recognition. At the start of the day the system detected that a
gesture had occurred but classified it wrongly most of the time — roughly 51%
correct on the user's hardware against a 94.7% figure reported by the offline
validation split.

**Outcome: 78.8% on held-out live captures, all five gestures, verified in the
user's own environment.**

---

## 2. Headline Result

| Stage | Held-out live accuracy |
|---|---|
| Start of day (no live data) | **51.5%** |
| + live SWIPE_LR | 94.6% / 89.7% (LR only) |
| + SWIPE_RL, PUSH_IN | 88.2% (3 gestures) |
| + SWIPE_UD, label corrected | 83.7% (4 gestures) |
| **+ SWIPE_DU — final, all 5** | **78.8%** |

Per-gesture, on captures the model never trained on:

```
SWIPE_LR    14/16 = 87.5%
SWIPE_RL     5/9  = 55.6%   <- weakest
SWIPE_UD     7/9  = 77.8%
SWIPE_DU     7/9  = 77.8%
PUSH_IN      8/9  = 88.9%
OVERALL     41/52 = 78.8%

Recorded corpus: 125/125 = 100.0%  (no catastrophic forgetting)
```

The declining headline from 88.2% to 78.8% is **not** a regression — each step
added a class, and five classes is harder than three.

---

## 3. Root Cause: A ~26° Geometry Offset

Comparing physical descriptors between the training corpus and the user's live
captures isolated the problem to two channels:

```
descriptor      recorded      live        verdict
range cog        26.38        26.75       ok
amplitude         0.91         0.68       ok
doppler          +0.18        +0.31       ok
azimuth          +0.36        -1.05       MISMATCH (d=1.51)
elevation        +0.39        -1.10       MISMATCH (d=1.58)
```

Both angle channels shifted by ~1.45 rad — **≈26°** — and by nearly the same
amount on two *independent* apertures (TX baseline and RX baseline):

```
SWIPE_LR   az -1.42  el -1.48
SWIPE_RL   az -1.49  el -1.48
PUSH_IN    az -1.39  el -1.29
           spread: 0.10 rad
```

A common offset on independent baselines is geometry, not gesture variation. The
hand sat ~26° off-axis relative to where the corpus was recorded. **No offline
metric could see this** — it took live captures from the deployment environment.

Fix: fine-tune on live captures so the model learns the actual geometry.

## 4. Errors Found and Fixed

### 4.1 Radar streaming stalled at `[WARMUP] 2/200` — FIXED
A timestamp tolerance gate added earlier compared the SDK's `timestamp` (an
integer tick count) against `0.05` seconds. Nearly every frame pair was rejected
and the queue starved.

`x7_2s_record.py` reverted to sequence-number pairing (byte-identical to the
known-good version). Stall detection added so this failure reports itself:

```
[WARN] No synchronised frame pair for ~6s (2 frames received so far).
```

### 4.2 Debug tool loaded an 8-channel checkpoint into a 10-channel model — FIXED
When the feature extractor moved to 10 channels, `x7_2s_live.py`'s default was
updated but `x7_2s_debug_live.py` was missed, producing a `size mismatch`
RuntimeError. Both now default to the same ensemble.

### 4.3 Gesture class names were inverted — FIXED
```
index 2  name="SWIPE_UP"    folder=G03_SWIPE_UD  ("Up -> Down swipe")
index 3  name="SWIPE_DOWN"  folder=G04_SWIPE_DU  ("Down -> Up swipe")
```
The display names meant the **opposite** of their folders. Following the name,
the user's Up→Down captures were labelled index 3 — the wrong direction. Training
on that would have taught the model backwards; the run was killed mid-training.

Renamed to match folder semantics: `SWIPE_UD` (Up→Down) and `SWIPE_DU` (Down→Up).
After relabelling to index 2, that gesture went **25% → 88.9%**.

### 4.4 Session-grouping bug produced a misleading 44.8% — FIXED
The held-out-session test grouped captures on gaps > 10 minutes. The user's
PUSH_IN recording began **37 seconds** after SWIPE_RL ended, so both were merged
into one block — holding it out left *both* classes with zero live training data.

This caused an incorrect claim that the user needed to re-record. The data was
fine; the test code was wrong. Replaced with a per-gesture chronological 75/25
split, which also tests on the *last* captures performed (harder than random).

### 4.5 Latency optimisation — APPLIED, THEN REVERTED
Offline simulation indicated a shorter post-peak wait was both faster and more
accurate:

```
post-peak wait   latency   simulated accuracy
40 frames         1.00 s     94.3%
32 frames         0.80 s     95.2%
24 frames         0.60 s     91.9%
16 frames         0.40 s     85.2%
```

Applied (~0.90 s typical). **The user reported live accuracy was much worse, and
it was reverted.**

Why the simulation was wrong: it truncated already-captured windows and
edge-padded them. Live, a shorter `POST_PEAK_FRAMES` also changes *when the
capture triggers and where the peak lands* — the whole state machine shifts. The
proxy could not model that. Same failure mode as §4.4: an offline test that did
not reproduce the live path.

All five constants restored: `DECAY_FRAMES=6`, `POST_PEAK_FRAMES=40`,
`MAX_GATHER_FRAMES=110`, `COOLDOWN_AFTER_HIT=20`, `COOLDOWN_AFTER_MISS=8`.

## 5. Physics Investigation

Asked whether alternative signal processing could suit the X7 better. Measured by
leave-one-burst-out — the only metric that predicted live behaviour (LOBO
predicted 60%, observed 58.1%).

```
representation             LOBO      note
current 8-channel         ~61%
+ 4th MIMO channel        70.5%     <- adopted
range-Doppler map (13ch)  63.8%
multi-lag Doppler (12ch)  63.2%
all three combined (22ch) 58.8%     <- worse than baseline
3-model ensemble          +2.9
test-time augmentation    +0.3      <- rejected
```

**The X7 provides 2 TX × 2 RX = 4 virtual channels; the code used 3 and discarded
`tx1_rx1`.** Pairing it with `tx0_rx1` gives a second horizontal baseline on the
other receiver — extending the transmit aperture and providing a redundant
azimuth estimate that averages out per-session phase offsets. Worth ~9 points.
Feature extractor now emits 10 channels.

The Doppler reformulations each help alone but are **redundant with the MIMO fix
and harmful stacked on top of it** — with ~95 recordings per class, 22 channels
gives the network more session-specific detail to memorise.

## 6. Hypotheses Tested and Rejected

Before live captures identified the real cause, these were measured and ruled out:

| Hypothesis | Result |
|---|---|
| More real recording sessions | 1→80%, 2→75%, 3→73% (single fold); multi-fold later showed sd collapsing 34%→7.9% at n=3 |
| More synthetic data | 1×/4×/8× copies → 45.8% / 44.8% / 46.3%, flat |
| Smaller / more regularised model | 62% → 55% → 53% → 37%, monotonically worse |
| Cross-session augmentation | LOBO 66→76%, but live captures **58.1% → 48.4%** |
| Mounting angle | 10° costs 1%; 30° still 79% |
| Sensor order swapped | would give 42.7%; pattern did not match |
| Time-reversed buffer | would give 2.0% |

**Synthetic data cannot substitute for real sessions.** It worked for the
occupancy model because that signal is aggregate energy, which is genuinely
synthesisable; gesture recognition depends on Doppler phase structure that
aliases differently every session (±0.41 m/s unambiguous at 40 FPS; per-session
phase spread up to 3.08 rad, near the full ±π range).

## 11. Lessons

**Offline proxies repeatedly disagreed with live behaviour**, and live was always
right. Three separate times — the replay harness, the session-grouping test, and
the latency simulation — an offline measurement pointed the wrong way because it
did not reproduce the full live path including the capture state machine.

**Leave-one-burst-out was the only offline metric that predicted reality**
(predicted 60%, observed 58.1%). The per-file validation split reported 94.7% for
a model that achieved 51.5% in the room, because it sampled the same recording
sessions on both sides of the split.

**The decisive fix was data from the deployment environment**, not architecture,
features, or synthetic augmentation.
