# Engineering Log — Dual-Sensor X7 Radar
**Date:** September 21, 2026

---

## 1. Session Objective

Train the presence model on the completed dataset ("we are done with capturing
all scenarios"), then run live detection with it.

**Outcome:** training produced 99.7% — and a control proved the number
meaningless: each occupancy level had been recorded on its own day, so the
label was perfectly aliased with the session. The recorder was redesigned to
interleave occupancy levels, a dataset gate was added, and the live path was
found to be ~13,000x too slow because the radar SDK blocks the Python
interpreter; acquisition was moved to its own process. The session ended with
the radar locked by a process this session had orphaned.

| features | occupancy accuracy |

## 4. Training — 99.7% That Means Nothing

Chronological 75/25 split within every scenario (570 train / 180 test), CNN,
10-channel features, 2 seeds:

| run | test accuracy |
|---|---|
| A — full features | 99.7% |
| B — **only bins 3.55-6.55 m (no seat there)** | **99.7%** |
| C — full + far-field normalisation | 99.2% |
| majority baseline | 40.0% |

A region with no occupants classifies occupancy perfectly. The checkpoint was
renamed `models/presence_v2_CONFOUNDED_DO_NOT_USE.pth`.

## 5. Diagnosis Revised Within the Session

The first explanation — a per-day noise-floor drift — was tested and **did not
hold**:

```
sitting   n    span    r(elapsed time, far-field energy)
09-11     50   13 min   +0.06
09-15    200   64 min   -0.07
09-16    300   96 min   +0.11
09-21    200   54 min   +0.02      all not significant
```

Far-field energy varied with seat arrangement, not with clock time. The
conclusion was corrected from "the model learnt the date" to "the accuracy is
**unfalsifiable**": counting occupants and recognising the session make
identical predictions on every possible split of this data.

(A second explanation offered here — multipath inside a metal car cabin — was
also wrong; the recordings were made in a room. Corrected Sep 22.)

## 6. Recorder Redesigned — Interleaved Sessions

`x7_2s_record_presence.py`, `run_session`:

- records in **rounds**; every round visits every scenario once in **reshuffled
  order**; `--block` (default 5) back-to-back trials per visit, repeated until
  every scenario has its full trial count
- filenames carry an explicit **sitting id** (`S01-09211425`) so sessions are
  grouped exactly instead of inferred from timestamp gaps
- warns when a session contains only one occupancy level
- `--countdown` (default 3 s) and `--countdown-empty` (default 15 s): empty
  trials need everyone, including the operator, clear of the radar

Dry run (no hardware, 16 scenarios incl. empty, 6 trials, block 2): every class
spread across the whole session, mean position 0.46-0.56, range ≈ 0.0-1.0.

## 7. New Tool — `check_confound.py`

Gate a dataset before training on it; accepts several folders
(`--data human_dataset_v2 human_dataset_v3`).

1. **Sitting balance (hard gate)** — every class must appear in more than one
   sitting.
2. **Region predictability (diagnostic)** — non-seating regions vs chance.
3. **Within-sitting time drift (diagnostic)**.

Verdict on v2: **NOT INTERPRETABLE** — all four classes confined to one sitting
each.

## 8. Live Detection — The SDK Blocks the Interpreter

The user asked to run live detection with the trained model as it stood. The
default classes file listed 5 classes and the model had 4, so
`models/presence_v2_classes.json` was created.

The first live run produced **one prediction every ~30 s** (0.03 fps).

| measurement | result |
|---|---|
| inference, no radar | 0.7 ms |
| inference, radar streaming | **13,000 ms** |
| CPU used during that call | **0.01 cores** (system 0.5 of 24) |
| SDK callback rate / CPU | 20/s, 0.1% |
| after `radar.close()` | still slow |
| `sys.setswitchinterval` 5 → 200 ms | worse: 15.6 → 23.6 s |
| process priority (SDK raises 32 → 128) | restoring it changed nothing |

Nothing was computing: the main thread was blocked. The Novelda callback SDK
calls into Python from native threads and holds the GIL across its wait for the
next frame. Recording never noticed because it does almost nothing between
frames.

**Fix — new `x7_acq_worker.py`:** the radar runs in a separate **process**
(`RadarProcess`, same `get_frame()` / `close()` interface); frames (7 KB) cross
a pipe. Result: inference 13,000 ms → **1.5 ms**, sustained **4.7-4.8 fps**.
`x7_2s_live_presence.py` uses it by default (`--in-process` keeps the old path
for diagnosis) and prints live fps.

Live output with one person present: steady `1 Person` at 92-94%. Weak
evidence either way — and the model has no empty class, so an empty cabin would
also read "1 Person".

## 9. The FTDI Lock

The user's next run failed with

```
Could not find a FT4222 device configured in mode 0. Check the hardware
connection and make sure that the DCNF0/1 jumpers are in position LL.
```

The hardware was fine — all four FT4222H interfaces enumerated `OK`. An
acquisition child from a live run this session had killed with `timeout`
(**PID 22052**) was still holding the device, which is exclusive-access.
`daemon=True` does not help: daemon children are reaped by the parent's atexit
handler, which a hard kill never runs. The orphan terminated but stayed wedged
in the FTDI driver; the shell was not elevated, so a USB replug was required.

**Fixes:**
- child **watchdog**: polls the parent every 2 s and hard-exits when it is gone
- `find_stale_workers()` / `clear_stale_workers()`
- a **preflight check** in both `x7_2s_live_presence.py` and
  `x7_2s_record_presence.py` that kills orphans and, if one is wedged, prints
  the replug instruction instead of letting the SDK blame the jumpers

## 10. Errors Introduced During This Session

1. **The orphaned worker (§9)** — a live test run was killed with `timeout`
   before orphan safety existed. It locked the radar until a USB replug.
2. **Over-broad `taskkill /IM python.exe`** — used to clear the stalled first
   live run, it also terminated two unrelated Python processes of the user's
   that had been running since 11:25. Later stops used explicit PIDs.
3. **Two premature explanations** (§5): day-specific noise drift, then
   metal-cabin multipath. Both were stated before being tested; the first was
   corrected the same day, the second on Sep 22.

## 13. Lessons

**Run the control before reporting the number.** 99.7% was one line of output;
"a classifier on bins with nobody in them also gets 99.7%" was the finding.

**Test an explanation before stating it.** Both first-draft explanations of the
confound were plausible and wrong. The drift test took two minutes.

**A blocked thread uses no CPU.** 0.01 cores during a 13 s call ruled out every
"it's too slow" hypothesis at once and pointed at a lock.

**Clean up hardware-owning processes by construction.** The FTDI lock and its
misleading jumper message came from a test harness killing a parent process —
the child must watch for that itself.

**Kill by PID, never by image name.**
