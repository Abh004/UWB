# Engineering Log — Dual-Sensor X7 Radar
**Date:** September 29, 2026

---

## 1. Session Objective

This session was all gesture recognition. Presence was finished on Sep 28.

1. Check the deployed gesture model at the current mounting and compare its
   radar configuration with the presence configuration.
2. Increase accuracy and precision at the same detection and prediction speed.
3. Build the new pipeline (recorder, trainer, live mode) and record data at the
   current mounting.
4. Improve live detection without rotating the boards. (The team chose to keep
   the current orientation.)
5. Fix slow calibration and calibration prompts that did not trigger.

**Outcome:** the gesture pipeline was rebuilt as `x7_gesture_*`. It uses 40
FPS, a 64-frame window, the same trigger in recording and live, and a small CNN
on coherent angle and amplitude. There are four sessions (218 captures) at the
current mounting. Accuracy on a held-out session rose from **41% to 77%**. Four
bugs were found and fixed on the way: a threshold-selection bug, slow
fine-tuning, a warm-up that fixed the trigger too high, and a training-set
confidence floor far too strict for live use.

## 2. Starting Point

### 2.1 The deployed model at the current mounting
The Sep 28 captures at the current mounting (`cal1`, 56 swipes) were scored
with the deployed model, and compared against one of its own training sessions:

| data | accuracy | median confidence (correct / wrong) |
|---|---|---|
| training session `s2` (50) | 100% | 0.97 / -- |
| current mounting `cal1` (56) | **7%** (below chance) | 0.66 / **0.71** |

At the current mounting the deployed model is confidently wrong. Left and right
are swapped, and up and down are mostly read as left or right. This fits the
Sep 28 finding that each board measures angle along one axis only, so a model
trained at one mounting is wrong at another.

### 2.2 Radar configuration: gesture vs presence
The request was to make the gesture configuration match presence. The two
presets were compared:

| setting | gesture (default_preset) | presence (effective) |
|---|---|---|
| RadarSource.FPS | 40 | 5 |
| RadarSource.IterationsPerFrame | 6 | 1400 |
| RadarSource.MframesPerPulse | 6 | 7 |
| RadarSource.PulsePeriod | 12 | 8 |
| 14 other settings (TX power, masks, DC removal, ...) | identical | identical |

They were **not** made the same. Presence integrates 1400 iterations at 5 FPS
to pick up breathing, while gestures need 40 FPS to follow a hand. The
presence preset would make gesture timing 8× coarser. Both still use the same
acquisition worker (Section 3.1).

## 3. New Pipeline (v3)

### 3.1 Files

| file | role |
|---|---|
| `x7_gesture_core.py` (new) | constants, trigger (`Segmenter`), features, model, `GestureModel.decide()`. Used by all three scripts below, so recording and live cannot drift apart |
| `x7_gesture_record.py` (new) | shuffled recording at the current mounting, through the same trigger as live |
| `x7_gesture_train.py` (new) | leave-one-session-out evaluation, threshold choice, 3-seed ensemble |
| `x7_gesture_live.py` (rewritten) | warm-up, optional session calibration, live recognition |
| `x7_acq_worker.py` | new `kind="gesture"`: the gesture radar (40 FPS) in its own process and reporting its range map. The presence path is unchanged |

### 3.2 Design
* **Timing:** 40 FPS, 64-frame window, peak-driven capture. Detection and
  prediction speed are the same as the old `x7_2s_live.py`.
* **Trigger:** moving energy in physical bins 20–33, relative to the noise
  floor behind the antenna (bins 0–15). The background adapts slowly (EMA,
  τ = 2 s), so a moving hand is not absorbed into it. The trigger is 6× the
  idle level from a 3 s warm-up. This replaces raw energy against a fixed
  threshold, which depended on the room.
* **Features:** each board is a 3-element line array (Sep 28), so its four
  single-baseline pairs are averaged coherently into **one angle per board**
  (a unit phasor). Z-scored amplitude is added, and Doppler is optional.
  Shape (2 boards, C, 14 bins, 64 frames).
* **Model:** two-branch CNN with ~113k parameters (the old model had 11.6 M).
  Three seeds are ensembled.
* **Classes:** SWIPE_LR, SWIPE_RL, SWIPE_UD, SWIPE_DU, PUSH_IN, NO_GESTURE.
  NO_GESTURE captures are non-gesture movements that trip the trigger, and
  teach the model to stay silent.
* **Recorder:** gestures come in shuffled blocks of 2, and never the same
  label twice in a row. A gesture that does not trigger is retried up to
  3 times. Press `x` to discard the last capture. Files are named
  `LABEL_SESSION_ts_idx.npy`, with session `G%m%d%H%M` by default.
* **Evaluation:** leave-one-session-out only. The old random per-file split
  overstated accuracy by ~14 points (Sep 28).

### 3.3 Check on the old corpus
The core was first run leave-one-subject-out on the 4-subject corpus (476
windows, no NO_GESTURE):

| channels | raw accuracy | at confidence >= 0.9 |
|---|---|---|
| angle | **72.3%** | precision 96.6%, recall 36% |
| angle + amp | 70.0% | precision 95.8%, recall 33% |
| angle + amp + doppler | 72.7% | precision 97.1%, recall 21% (at 0.95) |

This is on a par with the old CNN (73.7%) at 1% of its size. Angle only was
made the first default. Section 4.2 shows that was the wrong choice for the
current mounting.

No calibration sessions (`C…`) were saved. Every live calibration attempt was

### 4.2 First model and the threshold bug
The first model (11:21, 2 sessions, angle only) scored **40.6%** raw on a
held-out session. It chose a confidence floor of **0.30**. Live, the
observation was: "above 90% it is right; below 70% almost everything is wrong".

**Bug in `choose_thresholds`:** when no floor reached the target precision
(95%), the fallback maximised *recall*, so it picked the lowest floor. It now
maximises precision, subject to recall >= 15%. The old model was moved to
`models/_gesture_v3_bugged_threshold/`.

### 4.3 What each change adds (2 sessions, leave-one-session-out)

| input | raw acc. | at >= 0.6: precision / recall | at >= 0.8: precision / recall |
|---|---|---|---|
| angle | 40.6% | 48% / 29% | 36% / 9% |
| angle + time reversal | 50.0% | 46% / 32% | 49% / 17% |
| angle + amp | 46.1% | 53% / 27% | 58% / 15% |
| **angle + amp + time reversal** | **53.9%** | **65% / 47%** | 53% / 20% |
| angle + amp + doppler | 51.6% | 68% / 38% | 52% / 13% |
| angle + amp + doppler + time reversal | 45.3% | 54% / 37% | 59% / 20% |

* **Time reversal** means playing a capture backwards and swapping its label
  (LR↔RL, UD↔DU). It doubles the data for free, and is physically exact for
  swipes. PUSH_IN and NO_GESTURE are not reversed.
* **Amplitude** helps at the current mounting, even though it did not transfer
  across people in the corpus. The trainer default is now `angle+amp`, with
  reversal on.
* **Pretraining on the old corpus hurt** (41% → 21%): its mountings contradict
  the current one. The option `--pretrain-corpus` remains, but is not used.
* The retrained 2-session base model scored **54.7%**.

### 4.4 Session calibration (measured offline)
Fine-tuning on k captures per class from the held-out session, then testing on
the rest of that session (3 random draws):

| k per class | time | accuracy | at >= 0.8: precision / recall |
|---|---|---|---|
| 0 | -- | 53.9% | 52.6% / 20% |
| 1 | ~1 min | 57.2% | 70.9% / 38.9% |
| 2 | ~2 min | 67.3% | 75.7% / 41.7% |
| 3 | ~2 min | 69.2% | 79.8% / 42.9% |

This became live calibration: 2 per class by default, fine-tuned 15 epochs at
lr 5e-4, with the stored dataset mixed in and the calibration captures
weighted ×8. After calibration the confidence floor is at least 0.8.

### 4.5 More per session, or more sessions?
The question was whether to record gestures separately into a dataset folder
or record more sessions. A model trained on k captures per gesture from one
session and tested on the other gave:

| k per gesture | 2 | 4 | 6 | 8 | 10 |
|---|---|---|---|---|---|
| held-out accuracy | 39.5% | 46.1% | 47.7% | 50.8% | 49.2% |

Accuracy stops improving at ~8 per gesture. Beyond that, what varies from
session to session (position, pace, the room) matters more than the number of
repetitions. Every session already goes into `gesture_dataset_v3/`, so the
answer was **more sessions**, and two more were recorded (G09291203,
G09291208).

### 4.6 The 4-session model (12:15)
Held-out session, 218 captures: **raw accuracy 77.1%** (2 sessions: 54.7%).
The trainer chose confidence 0.95 (precision 94%, recall 17%). That is too
strict for live use:

| floor | precision | gestures recognised | wrong reports |
|---|---|---|---|
| 0.50 | 79% | 74% | 36 |
| 0.70 | 83% | 61% | 22 |
| **0.80** | **86%** | **47%** | **14** |
| 0.90 | 88% | 27% | 7 |
| 0.95 (trainer's choice) | 94% | 17% | 2 |

**Recommended live setting: `--confidence 0.8`.** On a fixed setup,
calibration is optional (`--calibrate 0`). It no longer needs to run every
time, because the base model now covers this mounting.

## 5. Live Calibration Problems

### 5.1 Fine-tuning appeared to hang
Fine-tuning three models ran in the same process as the radar. Its SDK
callback threads hold the Python GIL while waiting for frames (the same
effect measured for presence: 1 ms of work took 13 s). The live output stuck
at "fine-tuning".

**Fix:** fine-tuning runs in a separate spawned process (`_finetune_worker`),
and the radar keeps being read meanwhile. A dry run with a fake radar took
11–16 s. Captures are saved before fine-tuning, so an interrupted run no
longer loses them. It gives up after 240 s and keeps the base model, and
Ctrl+C skips it.

### 5.2 Calibration prompts did not trigger
While performing the calibration gestures, prompts showed "no movement
detected" or "skipped".

Hypotheses tested on hardware and **ruled out**:

| hypothesis | measurement | result |
|---|---|---|
| processing falls behind, gestures arrive after the window closes | in-process radar: 40.0 FPS, backlog <= 0.8 s over 30 s | not the cause |
| noise reference (bins 0–15) rises during gestures and cancels the hand energy | reference ×1.0 while hand energy rose 56–98× | not the cause |

Kept anyway as safeguards: the gesture radar runs in its own process (41.3
FPS); the frame queue is flushed at every GO; a lag check warns and flushes
beyond 0.5 s of backlog.

**Likely cause:** the idle level was measured **once** in the 3 s warm-up and
never updated. Movement during the warm-up (sitting down, reaching for the
keyboard) made it too high. The trigger (6× that level) then stayed too high
for the whole run, so smaller gestures never crossed it.

**Fix (`x7_gesture_core.Segmenter`):**
* The idle level is re-estimated every second, from the 20th percentile of the
  last 30 s.
* It can only go **down** from the warm-up value. Without this cap, continuous
  gesturing in replay pushed the level up 4× (113 → 446), which would cause
  the same misses.
* In replay, a spoiled warm-up now recovers and a clean one is unchanged. Both
  caught 14 of 14 gestures in 60 s.

**Diagnostics:** after GO, both the recorder and live calibration now show
`energy N.Nx idle / trigger 6x`. If the radar stops sending frames for more
than 2 s, they show `radar sends NO FRAMES for N s` instead. A missed gesture
now shows whether the energy was too low or no frames arrived.

**Not yet verified on hardware.**

## 10. Lessons

**Choose the threshold for the goal, and check what the fallback does.** Both
threshold problems (0.30, then 0.95) came from a rule that was correct only
when the target precision was reachable. One live observation ("above 90%
right, below 70% wrong") exposed the first.

**Measure before building a fix.** The frame-backlog explanation was
plausible, and a safeguard was built for it, but the hardware test showed 40
FPS with no backlog. The real candidate was elsewhere.

**An adaptive estimate needs a direction limit.** Letting the idle level adapt
freely fixed a spoiled warm-up but broke under frequent gesturing. It is safe
only because it can go down and never up.

**Sessions beat repetitions.** Accuracy stops improving at ~8 captures per
gesture within one session. What varies between sittings is what the model has
to learn.
