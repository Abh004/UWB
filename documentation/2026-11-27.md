## 3. Packaging

### 3.1 Choices
* **PyInstaller, one-folder build.** A one-file exe would unpack ~400 MB to a
  temp folder at every start, and complicates the worker processes.
* **CPU-only torch** in a separate build venv (`.venv-build`). The models are
  three 470 KB CNNs; the CUDA build in `.venv` is 2.7 GB on its own. Result:
  547 MB, of which torch 361 MB, numpy 27 MB, SDK 15 MB.
* **Models and data next to the exe**, not inside the bundle: they can be
  swapped without rebuilding, and calibration writes to them
  (`presence_calib.json`; gesture calibration saves its captures into
  `gesture_dataset_v4_pause\` and fine-tunes on that set). The launcher changes
  to the exe's folder at start, so the scripts' relative defaults work
  unchanged.
* **Console kept.** Calibration prompts and key presses (`msvcrt`) use it.
* **One launcher** (`x7_app.py`): `combined`, `gesture`, `presence-setup`,
  `demo`, `gui-demo`, `selfcheck`, plus a menu when started without arguments.
  Arguments after the mode go to the original script unchanged.

### 3.2 Problems found

| # | problem | effect | fix |
|---|---|---|---|
| 1 | SDK, wrapper and preset paths hard-coded as `C:\RR_02\...` in three recorders; `Utils` found only through this PC's `PYTHONPATH`; SDK DLLs through `PATH` | radar cannot open on any other PC | `x7_paths.py`: one place that knows the source and the bundle layout; `fix_firmware_path()` rewrites the absolute firmware path stored in the presets |
| 2 | system Python is **3.10.0**; its `dis` module has a bug that crashes PyInstaller (`IndexError` in `_get_const_info`, fixed in 3.10.1) | build fails | standalone Python 3.10.22 via `uv python install 3.10`; system Python untouched (`.venv` depends on it). 3.10 is required by the SDK's `PySignalFlow.cp310` |
| 3 | `GestureDisplay` started the window as `sys.executable <this .py> --child` | in the exe there is no `.py` | the exe starts itself with `--gui-child`, handled before torch is imported |
| 4 | `find_stale_workers()` looked only for `python*` processes running `spawn_main` | orphaned packaged workers (`X7App.exe --multiprocessing-fork parent_pid=N`) would keep the radar locked | match both forms; parent PID by regex. Checked against a real packaged worker's command line |
| 5 | `radar_direct_callback.py` puts the repo's SDK folder first on `sys.path` when it exists | on this PC the exe would load the repo's SDK, hiding missing files | the bundled `PySignalFlow` is imported first in a packaged run; `selfcheck` fails if it came from anywhere else |
| 6 | the `.sfl` flows load a Python node **by name** when streaming starts: `BasebandPlotter.radar_direct_param_node.RadarDirectParamNode` | first live run of the exe: `FlowConfigurationError: could not assign python module and/or class` | file bundled under `radar\BasebandPlotter\`; `selfcheck` now imports every node named in the flow files |
| 7 | when the SDK's stream thread died (as in #6), the worker stayed alive and the parent printed `SENSOR FAULT: no frames` forever | the user's run hung, still holding the radar and locking the exe | `threading.excepthook` in the worker sends the error upstream and ends the worker; `RadarProcess.get_frame()` raises it. Applies to source runs too |
| 8 | Windows does not pass redirected handles to multiprocessing children | the worker's output, including the SDK's own errors, is lost when output goes to a file | `X7_WORKER_LOG=<file>` sends the worker's Python and native output there |

### 3.3 Stuck radar after forced stops
During testing, several live runs were stopped with `Stop-Process -Force`.
Afterwards **neither the exe nor the source scripts got frames**: all 4
FT4222H interfaces present, no orphaned process, no error, just
`SENSOR FAULT: no frames`. The source version had streamed normally a few
minutes earlier. Replugging both USB cables cleared it, and the exe then
worked live. Stop live runs with Ctrl+C; the README now says so, and lists
this symptom under hardware checks.

* Target PCs still need the FTDI FT4222 driver (Windows usually installs it)

  (`Novelda_Evaluation_SLA_1.0.rtf`): check it before giving the app to anyone
  outside the team.

## 5. Lessons

* **A packaged app shows what the environment was doing for you.** Three of
  the fixes (#1, #5, #6) were dependencies on this PC's `PYTHONPATH` and
  `PATH` that nothing in the code mentioned. Test in a stripped environment.
* **Check what loads at run time, not just at import.** The flow's Python node
  is only imported when the radar starts streaming, so every offline check
  passed. `selfcheck` now reads the node names out of the flow files.
* **A worker that fails must say so and stop.** A dead stream thread inside a
  live process looked exactly like a quiet radar.
* **Never force-kill a live radar run** unless a replug is acceptable.

## 6. Deferred: in-car / infotainment

Discussed, not started. Key points for when it is picked up:
* Android Auto and Apple CarPlay are phone projection: the app runs on the
  phone with template-only UI in approved categories. The radar cannot reach
  the phone, and presence must work with no phone and the ignition off. So
  neither platform can host this app directly.
* What does work without a phone app: the head unit maps gestures to the same
  media/volume commands as the steering-wheel buttons, which Android Auto and
  CarPlay already accept.
* A full custom UI is possible on **Android Automotive OS** (Android on the
  head unit) as an OEM app reading vehicle properties.
* That needs the engine split from the UI (the GUI's JSON event messages are
  already a usable contract), the gesture CNN exported to ONNX/TFLite, the
  features and presence logic ported to C++ (the SDK supports Raspberry Pi 4
  and Cortex-M4 hosts), golden tests against the recorded datasets, and a
  decision on per-user calibration, which currently fine-tunes with torch.
