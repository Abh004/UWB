# Engineering Log — Dual-Sensor X7 Radar
**Date:** September 25, 2026

---

## 1. Session Objective

Record the **bridging session** — every occupancy level on one day, in the same
setup as v2 — and use it to answer the question v2 could not: does anything
trained on v2 detect people, or only recognise sessions?

**Outcome:** the bridge answered it. The architecture behind the original 99.7%
count model scores **45%** on the new day; the physics-feature zone model,
trained on v2 only, scores **AUC 1.000 with 0% false alarm** for both
occupied/empty and front-row occupancy. The back row remains unreliable at this
sensor spacing. The final model was retrained on v2 + v3, and live detection —
which appeared to report a sensor fault — was fixed and verified on hardware.

## 4. The Gate Was Too Weak — Fixed

`check_confound.py` passed v2 + v3 as **usable**, because every class now
appeared in more than one sitting. But each v3 sitting still held a single
class, so that criterion proved nothing.

New checks: classes per calendar day, sittings holding ≥2 classes, days holding
≥2 classes. Three verdicts:

```

v2 + v3         PARTIAL -- 09-25 holds classes 0,1,2,3,4, so leave-one-day-out
                is valid; no sitting mixes classes, so do not evaluate within a day
interleaved     usable
```

## 5. The Bridge Test — Trained on v2, Tested on 09-25

New tool `x7_presence_bridge_eval.py`. The zone model used is the **v2-only**
fit (`models/presence_zone_v2only.json`), never one that has seen v3.

| model | result on the new day |
|---|---|
| **zone: occupied** | **AUC 1.000**, recall 100%, **false alarm 0.0%** |
| **zone: front row** | **AUC 1.000**, recall 97.9%, **false alarm 0.0%** |
| zone: back row | AUC 0.954, recall 100%, false alarm 53.8% — unreliable |
| count CNN, 5-class, full features | **45.4%** (balanced 55.3%), chance 20% |
| count CNN, bins > 3.55 m only | 31.5% (balanced 34.7%) |
| seat CNN | s1 81%, s2 81%, s3 49%, s4 40%; count 42.6% |

Front row per scenario: correct on every recording, including the re-recorded
`seats14`/`seats12`; `seats23` flagged on 75% of windows (covered by the hold).
Front-empty scenarios (seat 3, seat 4, seats 34, empty): 0% flagged.

Correcting the labels raised back-row AUC from 0.930 to 0.954: the mislabelled
files had placed a back-seat occupant under a "back empty" label.

**State machine on the unseen day** (v2-only model, 20 runs, 34 min):

```
missed-occupant   0.2% of decisions   (worst: lone back-seat occupant, 12 s)
false-occupied   29.8%                (the 60 s hold; empty runs were 180 s)
EMPTY after departure   77-89 s
```

### What this settles

1. The 99.7% of Sep 21 was session memorisation: its architecture drops to 45%
   on a new day.
2. Physics features with no absolute phase or amplitude, and 36 parameters,
   generalise across days for occupied/empty and the front row.
3. Back-row detection and per-person counting are limited by geometry
   (sensors 15-20 cm apart, back row ~11 dB weaker), not by data.

## 6. Correction — The Empty-Room Difference Is Physical

Far-field static profile, shape correlation (sensor 1):

```
                 09-11o 09-15o 09-16o 09-21o 09-22e 09-25e 09-25o
09-22 empty       0.43   0.51   0.47   0.56   1.00   0.86   0.60
09-25 empty       0.64   0.69   0.65   0.75   0.86   1.00   0.78
09-25 occupied    0.95   0.98   0.96   0.98   0.60   0.78   1.00
```

v3 occupied matches the v2 occupied days (same setup — a valid bridge). v3 empty
matches v2 empty, and both differ from occupied, on two independent days. The
difference is caused by the occupants themselves — bodies shadow the walls behind
them and reflect into far bins. The Sep 24 hypothesis that the operator caused it
is withdrawn (assuming the operator stayed put as planned).

Consequence: a no-seat control **cannot** diagnose occupied-vs-empty (it
responds to people). `x7_presence_zone.py` and the bridge evaluation now say so,
and rely on leave-one-day-out instead.

## 8. Live Detection — "SENSOR FAULT" That Was Not

```
[INFO] Radar returned 112 range bins -> -1.38 m .. +6.55 m
SENSOR FAULT: no frames -- occupancy unknown
```

Two bugs in `cmd_live`, written Sep 24 and never run on hardware:

1. The frame timer started when the acquisition process reported ready; the SDK
   then takes ~2.3 s to stream, so the 2 s fault threshold fired at startup.
2. During warm-up `update()` returned nothing, so with the new 60 s window the
   false fault line stayed on screen for a full minute.

**Fixes:** before the first frame the display shows "waiting for radar stream";
a fault is reported only after 20 s with no first frame (`--startup-timeout`),
or a >2 s gap once streaming; warm-up shows a countdown; live fps is printed;
`--duration` stops cleanly for tests.

**Verified on the radar (85 s):** first frame after 2.3 s, 4.0-6.0 fps,
countdown through warm-up, then 24 decisions — `OCCUPIED front Y back ?`,
p(occupied) 1.00, with an operator seated in front of the radar.

## 12. Lessons

**A bridge only has to break the alias you care about.** v3 was not recorded as
planned, yet one day holding every class was enough to make a cross-day test
valid — and that test decided everything v2 could not.

**Gates must test the property, not a proxy for it.** "Each class in several
sittings" was meant to stand in for "classes mixed within a session"; the first
dataset that satisfied the proxy without the property got through.

**Run safety-relevant code on hardware before handing it over.** The live mode
passed replay tests but its first real run showed a fault that did not exist.

## 13. Afternoon — Clearing Delay and the Back Row

**User report:** after a person left, `OCCUPIED` persisted for well over a
minute; the back row always showed `?`.

Both were by design (60 s window + 60 s hold; back row marked unreliable), but
the delay was measured and shortened, and the back row given a safe partial
output.

### Window and hold, measured on the held-out day (v2-only models, v3 replay)

| window | hold | missed occupant | EMPTY after leaving |
|---|---|---|---|
| 30 s | 10 s | 0.2% | 39 s |
| 30 s | 30 s | 0.2% | 59 s |
| 30 s | 60 s | 0.2% | 89 s |
| 60 s | 10 s | 0.5% | 66-68 s |
| 60 s | 60 s | 0.5% | 116-118 s |

The 60 s window, chosen on training data, was worse on the unseen day. The hold
floor comes from the leave-one-day-out predictions: the longest run of missed
30 s windows in any sit-down was **3 (~30 s)**, a lone back-seat occupant
(`seats3`, 09-21); for the front row, 2 (~20 s). A hold shorter than that would
briefly report EMPTY with someone seated.

**Final setting:** 30 s window, **45 s hold** → EMPTY about 60-75 s after
everyone leaves. `--exit-s` at `live` overrides the hold (shorter = faster but
risks flicker).

### Back row: "Y only"

An unreliable output may confirm an occupant but never claim the seat is empty.
Its confident threshold is set at 1% leave-one-day-out false alarm:

```
v2-only threshold, tested on v3:  back recall 89.6%, FA 7.7%, front-only scenes 0.0%
final model (v2+v3 LODO):         threshold 0.877, back recall 61.1% at 1% FA
display:                          Y when confident, otherwise ? -- never '-'
```

It still does not drive "occupied".

### Display

The status line now shows the motion value against its threshold and, while
OCCUPIED, which evidence is holding it and when it will clear:
`held by p occ 20s ago, clears in 25s if nothing new`.

Final model retrained: `train --data human_dataset_v2 human_dataset_v3 --window 3 --exit-s 45`.

## 14. Robustness — Calibration, Setup-Change Monitor, Self-Test

**Question:** how to make sure it works tomorrow if the setup changes slightly.
The sensors stay 15 cm apart (needed for gesture work), so the back row remains
"Y or ?" and calibration works per row.

### What was measured first (v2-only model, held-out v3, simulated changes)

| change | occupied recall / FA | front recall / FA |
|---|---|---|
| none | 100% / 0% | 97.9% / 0% |
| sensor gain +-6 dB | unchanged | unchanged |
| random antenna phases | unchanged | 91.7% / 0% |
| radar 21 cm farther | 95.0% / 0% | 77.1% / 0% |
| radar 35 cm farther | 86.7% / 0% | 54.2% / 0% |
| radar 14 cm closer | 100% / 0% | 100% / 11.5% |

Invariant by construction: gain, per-antenna phase, day-to-day drift. Fragile:
the fixed range zones.

**What detects a setup change (and what does not):**
- static-room fingerprint correlation: unchanged windows 0.46-0.9, a 21 cm
  move still 0.74 median -- **cannot separate**
- wall-reflector lag estimation: unchanged setup gives lags of -8..+8 bins --
  **cannot separate**
- coupling level: internal to the board, varies up to 36% naturally -- blind to moves
- **front-row breathing peak: works** -- same setup +0.5 cm median (daily
  -3.6..+5.2 cm, 10 s sd ~9 cm); moves of 7/14/21 cm read +7.6/+14.8/+21.9 cm.
  Back row too noisy (sd 12.7 cm) to monitor.
- **receiver reference noise**: sd 0.9 dB, max 3.3 dB across all days -> +-6 dB alarm

### Built

- `x7_presence_zone.py`
  - `row_peak()`; `zones_for()` shifts the trained zones by whole bins (widths
    unchanged); training stores `row_ref_m` (front 0.731 m, back 1.429 m)
  - `ZoneDetector(..., calib, auto_align)`: calibrated zones and motion
    threshold; **health monitor** -- front-row drift > 10 cm over >= 18 blocks
    (~3 min) -> auto-align (toward zero, max 30 cm) or `SETUP CHANGED,
    recalibrate`; reference noise > 6 dB for 30 s -> `check the radar`;
    calibration from a different model -> warning. Blocking warnings turn EMPTY
    into UNKNOWN (never claims an empty cabin).
  - `live --calib models/presence_calib.json` (default), `--no-auto-align`
- `x7_presence_setup.py`
  - `calibrate`: empty 60 s + one person per seat 45 s (~5 min). Measures row
    positions (dead band: front offsets < 5 cm are normal variation; back row
    follows the front unless they disagree by > 10 cm), motion threshold, noise
    reference; validates on its own captures; writes `models/presence_calib.json`
  - `selftest`: empty 100 s, seats 3, 4, 1, 2 (45 s each), optional all four,
    empty 100 s (~8 min). PASS/FAIL per step: no missed occupant after 10 s,
    front row right in the last 10 s, EMPTY within window + hold + 20 s, no
    health warnings. Report in `selftest_reports/`.
  - both accept `--from-files DIR` to test the procedure on recordings
- `x7_acq_worker.py`: preflight now counts FT4222H USB interfaces and says
  plainly when a board is not connected
- `test_presence_setup.py`: offline checks (below)

### Verified (offline, `test_presence_setup.py` -- all 10 checks pass)

```
radar +21 cm   old calibration: front recall 79.2%  -> recalibrated 97.9%, FA 0%
radar -14 cm   old calibration: front FA 11.5%      -> recalibrated recall 100%, FA 0%
auto-align     +21 cm move found after 5.0 min of front-row occupancy (aligned +29 cm)
no drift       10 min unchanged setup: no warnings
sensor fault   sensor 1 -12 dB: warning, status UNKNOWN (never EMPTY)
```

`calibrate` + `selftest --from-files human_dataset_v3 --all-seats`: calibration
shift 0 on the unchanged setup, self-test PASSED (7/7 steps).

### Errors found while building

1. Simulation of a closer radar scaled amplitude the wrong way (up to 11x in
   near bins); fixed to ((R - d) / R)^2. The -14 cm front FA of 11.5% survived
   the fix.
2. Calibration peak search reached the antenna near-field; now never searches
   closer than 0.35 m.
3. Rounding shifted zones on an unchanged setup (+4 cm -> +1 bin); dead band added.
4. Auto-align overshoot by 1 bin; now rounds toward zero. Remaining ~7-10 cm
   over-read of large moves is physical (R^-4 tilts an extended target's
   profile); zones are 0.7 m wide and detection recovers fully.
5. A heredoc mangled a `\n` escape into broken code in `x7_acq_worker.py`;
   repaired and all four modules syntax-checked.

### Not yet run on hardware

The live `calibrate` / `selftest` paths were exercised against recordings
only. The hardware smoke test failed because both radar boards had dropped off
USB (all four FT4222H interfaces `Present: False`). `models/presence_calib.json`
currently comes from the v3 recordings and must be replaced by a live
calibration.
