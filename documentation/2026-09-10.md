# Engineering Log — Dual-Sensor X7 Radar
**Date:** September 10, 2026

---

## 1. Session Objective

Opened with "nothing is working, it's all showing wrong" — live gesture output
felt like coincidence rather than recognition. The session became a full audit of
the live path, then of the sensor geometry, then of the range physics.

**The single most important outcome is a corrected constant:** the radar's range
bin length had been assumed at 6.5 mm from a source-code comment since the start
of the project. It is actually **71.4 mm** — wrong by a factor of 11 — and every
range figure ever quoted in this repository was derived from it.

## 3. The Range Constant — Root Cause

`probe_range.py` reads what the SDK reports in every callback, which the project
had never done:

```
data shape      (2, 2, 112)     (rx, iq, bins)
range_offset    -1.38 m
bin_length       0.0714 m       <- assumed 0.0065 m
coverage        -1.38 m .. 6.55 m
```

`range_offset` and `bin_length` are handed to `_frame_callback*` on **every
frame** and were discarded on every one. `x7_physics.BIN_LENGTH_M` was set from a
code comment instead.

### Corrected range map

```
PRESENCE, 112 bins:  -1.38 m .. 6.55 m
     0 m -> bin  19.3        3 m -> bin  61.3
     1 m -> bin  33.3        4 m -> bin  75.4
     2 m -> bin  47.3        6 m -> bin 103.4

GESTURE, 34 bins:    -1.38 m .. 0.98 m
     hand measured at bin ~26.6  ->  0.52 m
```

### What this invalidates

* **"Presence reaches only 0.72 m"** — wrong; it is 6.55 m.
* **"You cannot do room occupancy at this range"** — wrong.
* **"Gesture reaches 0.21 m; keep the hand within 21 cm"** — wrong. The span is
  −1.38 m to 0.98 m and the hand sits at **0.52 m**, which matches natural
  arm's-length gesturing and is far more physically plausible than 15 cm.
* The sensor-separation arithmetic (15–18 cm recommendation) was computed against
  the wrong working distance and **has not been redone**.

The *measured* geometry results (§6) are unaffected — they came from data, not
from the bad constant.

## 4. Errors Found and Fixed

### 4.1 Config / model mismatch — FIXED
`x7_2s_train.py` had been switched to **6 classes with PINCH** on Sep 9 while the
deployed ensemble was 5-class. Anything constructing a model from `N_CLASSES` and
loading those weights failed outright. Reverted to the 5-class set; both class
lists are retained in the file with a comment explaining the switch.

### 4.2 The 6-class model is catastrophic — REVERTED
On the 209 live captures then available:

```
m5_v5  (5-class, Sep 8)   198/209 = 94.7%
m6_v1  (6-class, Sep 9)    69/209 = 33.0%
```

PINCH absorbed **95 of 209 (45%)** as false positives — 33 SWIPE_LR, 21 PUSH_IN.
Cause: `debug_captures/` holds **zero live PINCH recordings**, so PINCH was
trained only on corpus geometry and its unconstrained decision region swallowed
live samples from every other class. This is why it was removed on Sep 8.

### 4.3 Mounting position changed between Sep 8 and Sep 9 — confirmed
Measured azimuth of the summed AoA phasor:

```
corpus  Aug 7      +1.10      position family A
corpus  Aug 11     -0.67      position family B
LIVE    Sep 8      -1.05      position family B   <- m5_v5 fine-tuned here
corpus  Sep 9      +1.87      position family A
LIVE    Sep 10     +1.53      position family A   <- current
```

The user confirmed the rig was moved between the 8th and 9th. **All 209 Sep 8
live captures, and the entire fine-tuning effort built on them, are specific to a
mounting position that no longer exists.**

Direct consequence: `m5_v5` scored 5/10 on today's captures while the older,
PINCH-crippled `m6_v1` scored 7/10 — because the latter contains Sep 9
position-A data.

### 4.4 Model collapse from mixing positions — FIXED
`m5_pos9` was trained on Sep 9 corpus (position A) **plus** the 209 Sep 8 live
captures (position B) weighted 2×. The two differ by ~2.6 rad on the AoA
channels, so the same gesture appeared under contradictory angular signatures.
The model resolved this by collapsing:

```
predictions across 50 live captures
  SWIPE_DU   27  (54%)
  SWIPE_LR   12  (24%)
  SWIPE_UD    7  (14%)
  SWIPE_RL    4  ( 8%)
  PUSH_IN     0  ( 0%)   <- never predicted once
```

Retraining on current-position data only stopped the collapse (spread became
17/15/10/6/2) though accuracy only moved 38% → 42%.

### 4.5 `MframesPerPulse = 29` preset rejected — REVERTED
Attempting to extend range by raising `MframesPerPulse` from 7 to 29 produced a
preset the radar silently refuses: the script starts, prints the preset path, and
never emits `Receiving BBIQ_FLOAT32`. **Every preset shipped with the SDK uses
7.** Reverted. The change was unnecessary anyway once §3 was understood.

## 5. Errors Introduced During This Session

### 5.1 Window-centring "fix" made live accuracy worse — REVERTED
`x7_2s_live.py` and `x7_2s_debug_live.py` compute the peak index by different
rules:

```python
# debug_live (produced every fine-tuning capture)
pk = len(arr) - 1 - since                      # trailing 5-frame energy peak

# live.py (production)
peak_idx = span_start + argmax(per-frame energy)
```

An offline test predicted aligning them would gain +4.3 points (94.7% → 90.4%
when re-centred). Applied — **the user reported live accuracy got worse, and it
was reverted.**

Why the test was wrong: it re-centred *already-extracted* windows, which injects
edge padding and biases the comparison toward the debug rule. The two paths still
differ; that is now documented in the source rather than silently "fixed".

### 5.2 The α orientation metric did not measure orientation
Proposed `α = atan(V_sweep / H_sweep)` to verify antenna alignment. It returned
52°/42° before the re-mount and 41°/47° after — **essentially unchanged despite a
real physical rotation.**

Cause: it used *unsigned* sweep magnitudes, and at close range a hand sweeps
through a wide angle in both azimuth and elevation regardless of orientation.
Replaced with a **signed** rotation test using an opposing gesture pair (§6),
which does respond correctly.

## 6. Sensor Geometry — Measured

### 6.1 The boards were rolled 45°, not angled inward
A photo revealed the two boards lying **flat on the surface, rotated in-plane**
(`\ /` as roll), not aimed toward each other. Boresights were therefore parallel,
and the 45° was rotating the antenna baselines onto diagonals.

### 6.2 Axis purity before and after re-mounting

Purity = separation on the channel's intended axis ÷ leakage from the other axis.
**1.0 means the channel is useless** — equally responsive to both axes.

```
                          45° (before)   upright (after)
S1 channel H (want horiz)      0.1x           10.8x
S1 channel V (want vert)       0.8x            0.2x
S2 channel H (want horiz)      0.3x            6.9x
S2 channel V (want vert)       0.5x            3.2x

MEAN                           0.4x            5.3x
```

At 45° **every channel was below 1.0**, and two were responding more strongly to
the *opposite* axis than their own — the "horizontal" channel was measuring
vertical motion. That is a physical explanation for the LR↔RL and UD↔DU
confusions pursued in software across two sessions.

After the user re-mounted upright with wider separation, three of four channels
are cleanly selective. `S1 channel V` remains weak (0.2×); vertical
discrimination now rests on sensor 2, which does it well.

Caveat: roll and separation changed together, so their individual contributions
cannot be separated.

### 6.3 Sensor balance
```
SWIPE_RL     0/11 bad        SWIPE_LR   7/15 bad  (first run, before settling)
SWIPE_DOWN   0/11 bad        ALL        median ratio 0.99
SWIPE_DU     0/19 bad
```
"Bad" = one sensor more than 2× the other. Centring improved markedly after the
first run.

## 7. What Actually Improves Live Accuracy

5-fold cross-validation over the 50 `s2` captures — train on the current-position
corpus plus 8 live captures per gesture, test on the 2 held out, rotated five
times so every capture is predicted by a model that never saw it:

```
                                  overall   LR    RL    UD    DU   PUSH
corpus only (375 recordings)         42%    80%   20%   50%   50%   10%
+ 8 live captures per gesture        62%    70%   50%   90%   40%   60%
```

**375 corpus recordings are worth less than 40 of the user's own captures.** The
corpus was recorded by a different person at a different standoff; that gap is
wider than the model can bridge. PUSH_IN went 10% → 60%, SWIPE_RL 20% → 50%.

## 8. Presence Recorder — Rewritten

`x7_2s_record_presence.py` now supports:

* **Seat scenarios** — `--seats N`; enumerates every seat combination per
  occupancy level and lets the operator select which to record. Occupancy stays
  in the folder name (`2_people/`) for pipeline compatibility; the arrangement is
  encoded in the filename (`2people_seats13_S01_<ts>_001.npy`).
* **Batch looping** — asks trials per scenario once, then runs the whole plan
  automatically with a 3-2-1 countdown per trial and a skip option.
* **Auto-detected bin count** — sized from the first frame the radar sends rather
  than hardcoded; short frames are dropped, never zero-padded.
* **`--fps`** — sets frame rate and integration together so they cannot drift:
  `IterationsPerFrame = 700 × (10 / fps)`.

### Why lower FPS was chosen (default 5)

```
breathing         0.20-0.33 Hz  ->  Nyquist needs only 0.66 Hz
10 FPS is ~15x more than the signal requires

  FPS   iterations   SNR gain   50-frame window   breath cycles
   10          700      0.0 dB          5.0 s       1.0 - 1.7
    5         1400      3.0 dB         10.0 s       2.0 - 3.3
    2         3500      7.0 dB         25.0 s       5.0 - 8.2
```

At 10 FPS a 50-frame window holds **barely one breath cycle**, which is too few
to establish periodicity — a limitation of the original design independent of
range. 5 FPS doubles the cycles seen and adds 3 dB, while keeping Nyquist above
heart rate (1.0–1.7 Hz).

## 12. Lessons

**Read what the hardware tells you.** The single largest error in this project —
an 11× range error propagated into every physical claim — persisted because
`bin_length` was assumed from a comment while the SDK supplied the true value in
every callback. One probe script settled it in seconds.

**Offline proxies kept disagreeing with the hardware, and the hardware was always
right.** Three times today an offline test pointed the wrong way: the windowing
"fix", the α metric, and (on Sep 8) the latency change. Each failed because the
proxy did not reproduce the full live path.

**Physical configuration silently invalidates everything.** A mounting change
produces no error, no warning — just degraded accuracy that looks exactly like a
software bug. Two sessions were spent debugging software for what was, in part, a
hardware change.

**The user's own data outweighs volume.** 40 captures from the deployment
environment beat 375 corpus recordings.
